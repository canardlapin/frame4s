# R5k.2 join anti-fitting baseline

This receipt fixes the pre-optimization behavior that R5k.3 must preserve. It
does not compare frame4s with another engine. Its job is to prevent a faster
aligned sorted fixture from being mistaken for a generally faster join.

The court covers ten deterministic workloads:

- aligned unique keys;
- offset unique ranges;
- interleaved keys with gaps;
- disjoint sorted ranges;
- duplicate groups with many-to-many output;
- a right side one tenth the size of the left;
- nullable keys;
- sorted keys split across unequal batch boundaries;
- independently shuffled keys;
- an otherwise sorted right side with its final two keys inverted.

The main component measures every workload at 1K, 4K, 16K, 64K, 256K, and
1M rows. The scale component measures nine workloads at 4M. Duplicate groups
are excluded at 4M because they produce eight million output rows; the 1M case
already measures two million outputs. Every timed cell has gather-view,
deep-materialized, and matched-consumption endpoints.

All workloads use the same optional `Int32` key schema so the nullable case
does not silently change the physical schema. Except in that case, every key
is present.

## Independent semantic oracle

Expected matches are generated by workload-specific closed-form maps, not by
calling another join implementation. Payloads contain source row ordinals, so
the ordered checksum distinguishes both left and right row order. Every cold
run, warm run, and timed setup validates exact cardinality and checksum.

All 69 size/workload configurations pass. The focused shared suite also proves
on JVM and Scala.js that a final-key inversion rejects merge dispatch and that
the hash result remains checksum-identical over three runs. The existing
cross-batch sorted test proves unique and duplicate stable order.

## Observed dispatch boundary

- Every workload uses hash below 16,384 rows.
- At 64K, aligned, offset, interleaved, disjoint, duplicate, and multi-batch
  sorted inputs use merge. Sparse stays on hash because its 6,400-row right
  side remains below the threshold.
- At 256K and above, every non-null sorted workload, including sparse, uses
  merge.
- Nullable, fully shuffled, and late-inversion workloads use hash at every
  size.

This rejects identity-only fitting. Offset, gapped, disjoint, duplicate,
sparse, and cross-batch inputs all reach the same merge implementation when
both sides cross the admitted threshold.

Sorted detection remains visible work. At 4M its warm cost is 20.65--31.58 ms
for the large sorted shapes. A late inversion costs 33.34 ms before selecting
hash, while a fully shuffled input rejects sorting after 0.028 ms. R5k.3 must
therefore retain early rejection and cannot treat detection as free.

## Materialization target

The matched endpoint remains dominated by physical output:

| Rows | Workload | Gather view | Deep output | Gather allocation | Deep allocation |
|---:|---|---:|---:|---:|---:|
| 1M | aligned unique | 22.666 ms | 140.896 ms | 32.01 MB | 204.02 MB |
| 4M | aligned unique | 86.312 ms | 654.683 ms | 128.02 MB | 816.04 MB |
| 1M | duplicate groups | 67.581 ms | 268.833 ms | 48.01 MB | 392.03 MB |
| 1M | multi-batch sorted | 38.514 ms | 178.882 ms | 40.02 MB | 212.03 MB |

At 1M the non-aligned sorted cases scale with emitted output: offset unique
emits 750K rows in 103.901 ms, interleaved gaps emits 333,334 in 41.581 ms,
and duplicate groups emits two million in 268.833 ms. The merge path is not
limited to the identity fixture. The remaining target is typed physical
materialization without generic scalar boxing.

The precommitted regression limits are unchanged: large shuffled time no more
than 1.03x this baseline, small tiers no more than 1.05x, fallback allocation
no more than 1.05x, and no cardinality, checksum, dispatch, ordering, JVM, or
Scala.js divergence. A result outside a narrow timing limit requires a fresh
interleaved confirmation; it is not waived by selecting a more favorable
sample.

`main/` and `scale/` retain JMH JSON and logs, normalized metrics, cold and warm
stage samples, environment details, exact validations, and key fingerprints.
`source-files.sha256` binds the receipt to the measured interpreter, fixture,
runner, script, and shared semantic test.
